## H1 — The v3 figure is a 2-bootstrap smoke and carries no information

**Verdict: SUPPORTED.**

The three runs used three different settings. Read from each run's own
manifest:

| run | `n_bootstraps` | `n_lambda` | profile | lambda source | glmnet |
|---|---|---|---|---|---|
| 0.1.0-era, unpacketed | 500 | 10 | — | `auto` implied | 5.0 |
| v2 sealed negative | 500 | 10 | `full` | pinned Python grid | 4.1.10 |
| v3 smoke | **2** | 10 | `smoke` | pinned Python grid | 5.0 |

- v2: `stablr-experiments/papers/application-note/artifacts/stablr-0.1.1-c59780093899/metadata.json:101-118`
- v3: `stablr-validation-artifacts/0.1.1/completion-20260920-fac5a622/smoke/ool-v3-smoke-20260920-58326937/metadata.json:115-133`
- the switch that produced the 2: `stablr-experiments/analysis/generate_ool_parity_v3.R:893-897`

The consequence is arithmetically decisive. At `n_bootstraps = 2` the R
stability score is a mean of two Bernoulli draws, so it lies in {0, 0.5, 1}. The
smoke's `fdr_min_threshold_` is 0.50, and `get_support()` uses a strict `>`
(`R/stabl_accessors.R:57-59`), so the selected mask is `score == 1.0`. R
selected 11 features, Python 7, the intersection is 6 and the union 12, giving

```
Jaccard = 6 / 12 = 0.5
```

which reproduces `ool_parity_results.csv` exactly. The Spearman collapse and
the 0.08 threshold delta are the same quantization artifact: R's score profile
has three levels with massive ties, while the Python profile has 576 of 1317
exact zeros and 7 features in [0.702, 0.998].

**The v3 smoke numbers are not a parity measurement and must not be compared
with the 500-bootstrap runs.** `full_profile` is a hard gate for exactly this
reason (`generate_ool_parity_v3.R:677`).

There is also a confound inside the 500-versus-500 pair: v2 ran glmnet 4.1.10
while the 0.1.0 run and the v3 smoke ran glmnet 5.0. v2 is therefore not a clean
repeat of the earlier run either.

## H2 — v2 used the wrong artificial-feature generator

**Verdict: SUPPORTED. v2's `random_permutation` was wrong for this comparison;
v3's `knockoff_equi` is right.**

The pinned Python reference resolves its user-facing `"knockoff"` to Gaussian
model-X equicorrelated knockoffs:

- `stablr-experiments/stabl-python/stabl/stabl.py:10` imports `GaussianSampler`
  from `knockpy.knockoffs`
- `stabl.py:1438-1454` runs `GaussianSampler(X, method='equicorrelated').sample_knockoffs()`
- `stablr-experiments/analysis/generate_ool_python_tutorial_scores.py:232-243`
  instantiates `Stabl(..., artificial_type="knockoff", ...)`, recorded as
  `"artificial_type": "knockoff"` in `ool_python_tutorial_metadata.json:39`

The same string means something different in `stablr`.
`R/artificial_features.R:192-243` implements `make_knockoff_features()` as
**fixed-X** knockoffs via `knockoff::create.fixed`, guarded by `n > p`. The OOL
matrix is 150 x 1317, so the guard fires and the typed-error handler falls back
to random permutation (`R/artificial_features.R:245-265`). The v2 packet records
precisely that:

```json
"requested_type": "knockoff", "actual_type": "random_permutation",
"fallback_history": [{ "from_type": "knockoff", "to_type": "random_permutation",
  "reason": "Input X must have dimensions n > p" }]
```

The fallback is correct fail-closed engineering. The error was requesting
fixed-X `knockoff` for a p > n design. v2 therefore calibrated FDP+ on permuted
features against a reference calibrated on Gaussian model-X equicorrelated
knockoffs — a different null distribution — so movement in Jaccard and Spearman
is expected and is **not** interpretable as a regression.

v3 requests `knockoff_equi` (`generate_ool_parity_v3.R:906`) and got it:
`requested_type == actual_type == "knockoff_equi"`, `fallback_counts: [0,0,0,0]`,
empty `fallback_history`, `shrinkage: 0.292888990789698`,
`initial_gamma: 0.58577798157929`.

**Caveat.** `generator_alignment` (`generate_ool_parity_v3.R:538-551`) validates
provenance metadata strings only. No gate inspects the generated knockoff
matrix. R uses `knockoff::create.gaussian()` plus `sample.int()`; Python uses
`GaussianSampler().sample_knockoffs()` plus `numpy.random.default_rng().choice()`.
Different RNG streams necessarily yield different null features. The generator
semantics are now correct; bit-identical artificial designs are unattainable and
currently unverified.

## H3 — The two scores are the same quantity

**Verdict: REFUTED as a defect. The Spearman comparison is valid in kind.**

Both sides compute the maximum over the lambda path of the per-lambda bootstrap
selection frequency.

- R: `R/stabl_accessors.R:408-413`, `get_importances()` returns
  `rowMaxs(object$stabl_scores_)`, where `stabl_scores_` is features x lambdas
- Python: `stabl.py:1352-1361`, `get_importances()` returns
  `np.max(self.stabl_scores_, axis=1)`
- the frozen column is literally named for it:
  `generate_ool_python_tutorial_scores.py:255-260` writes
  `python_max_score` from `np.max(estimator.stabl_scores_, axis=1)`, and
  `ool_python_tutorial_scores.csv` has 1317 rows

Support and threshold definitions are also matched: `R/fdp_control.R:93-120` and
`stabl.py:1468-1505` both use max-over-lambda scores, strict `>`, the
`(pi^-1 n_art + 1) / max(1, n_real)` estimator, the `min_fdr > 1` cap, and
first-index `argmin` tie-breaking.

One real methodological difference exists and is worth recording: v2 computed
Spearman over `intersect(names(r), names(py))`, so a partial-overlap
correlation was admissible (`generate_publication_parity_table.R:593-597`). v3
requires exactly 1317 identical unique finite names and aborts otherwise
(`generate_ool_parity_v3.R:553-567`). The tightening is correct, and it means
v2's 0.7847 is not a clean full-profile statistic.

**Unreached ceiling.** The two 500-bootstrap runs draw their resamples from
different RNGs: R uses `sample.int(150, 75, replace = FALSE)` under
Mersenne-Twister, Python uses `numpy.random.RandomState(42)` then
`rng.choice(150, 75, replace = False)`. Same seed and same subsample size,
disjoint algorithms. The two runs are therefore two independent Monte-Carlo
estimates of the same 1317-vector, which caps achievable Spearman below 1.0
irrespective of solver correctness. This is inference from code, not measured.

## H4 — The lambda bridge is misattributed, and one gate is a tautology

**Verdict: the `C = 1/(48*lambda)` bridge does not apply to OOL. The v2/v3
lambda grids are compatible. One gate cannot fail.**

The bridge lives in the package's own solver-parity fixture, not in the OOL
generator: `tests/testthat/fixtures/python_parity/generate.py:550-560`, where
48 is the bootstrap subsample size in that synthetic fixture (1920 rows / 40
bootstraps = 48, from `n_samples = 72`). OOL is `family = "gaussian"`
(`generate_ool_parity_v3.R:904`), so no bridge applies at all.

The v3 generator passes the pinned grid explicitly
(`generate_ool_parity_v3.R:892`), and `R/learner_adapters.R:520-532` sorts
descending for glmnet then maps results back column-wise, so column `j` of
`stabl_scores_` corresponds to pinned `lambda[j]`. Column alignment is sound.

For the record, `auto_lambda_grid()` is **not** compatible with the pinned Python
grid. Python uses `l_max = ||X'y||_inf / n` then
`alpha = geomspace(l_max/30, l_max+5, 10)` (`stabl-python/stabl/utils.py:45-46`).
Recomputing on the pinned standardized matrix gives `l_max = 24.5698501562`, and
the pinned ascending grid 0.818995 to 29.569850 matches to 5.68e-14. glmnet's own
10-value path over the same data is 24.56985 down to 0.246 — a maximum relative
difference of 29x. The penalty normalizations do agree. v3 avoids the problem
only because it supplies the grid; any future parity path that uses
`lambda_grid = "auto"` is unguarded.

**`lambda_alignment` cannot fail.** It compares `fit$fitted_lambda_grid` to the
pinned vector, but `R/stabl_fit.R:428` stores the supplied grid verbatim and the
generator builds that grid from the pinned CSV. `preprocessing_alignment` and
`generator_alignment` are similarly shape- and metadata-only. These are not
accusations; they are gates that carry no information and should either be
strengthened or removed.

The FDP-threshold delta is `abs(fit$fdr_min_threshold_ - 0.58)` where 0.58 is the
frozen Python constant. Both sides sweep `seq(0, 0.99, by = 0.01)`, so the delta
is quantized to 0.01 and the gate of `<= 0.05` means "within 5 grid steps". The
observed 0.08 is 8 steps: R 0.50 against Python 0.58, identically in v2 and in
the smoke.

## Measured: the `>= 0.90` Spearman gate is unreachable by construction

This was item 1 of "Required before any OOL number is quoted again", and it is
now settled.

**Method.** Five independent `stabl_fit` runs on the exact pinned OOL design —
150 samples, 1317 features after the pinned median/mean/scale transform, the 10
pinned lambdas, `family = "gaussian"`, lasso, `n_bootstraps = 500`,
`sample_fraction = 0.5`, `artificial_type = "knockoff_equi"` with
`artificial_proportion = 1.0` — differing only in `random_state`
(42, 43, 44, 45, 46). Spearman was computed between the resulting
max-over-lambda score vectors over all 1317 features.

The two runs share every modelling choice and differ only in which bootstrap
resamples were drawn. Any difference is therefore Monte-Carlo noise, not solver
disagreement. **This measures the ceiling a perfect solver could reach when
compared against a second run of itself.**

```
                    seed42   seed43   seed44   seed45   seed46
seed42                 NA   0.8313   0.8361   0.8369   0.8376
seed43            0.8313       NA   0.8488   0.8425   0.8490
seed44            0.8361   0.8488       NA   0.8291   0.8448
seed45            0.8369   0.8425   0.8291       NA   0.8293
seed46            0.8376   0.8490   0.8448   0.8293       NA

CEILING (mean pairwise R-vs-R Spearman) = 0.8385
range = 0.8291 .. 0.8490
frozen gate requires >= 0.90  =>  UNREACHABLE
```

Per-run detail:

| seed | features selected | `fdr_min_threshold_` | non-zero scores |
|---|---|---|---|
| 42 | 5 | 0.70 | 815 / 1317 |
| 43 | 6 | 0.73 | 877 / 1317 |
| 44 | 4 | 0.74 | 844 / 1317 |
| 45 | 5 | 0.77 | 798 / 1317 |
| 46 | 5 | 0.72 | 820 / 1317 |

**Conclusions.**

1. **The `score_spearman >= 0.90` gate in `OOL-parity-v3-protocol.md` cannot be
   met.** The measured within-language ceiling is 0.8385, and the range across
   seed pairs tops out at 0.8490. The gate is above the noise floor of the
   estimator it is applied to. This is a defect in the gate, not in the package,
   and it must be revised under a new protocol version. Running the expensive
   full profile cannot change this conclusion.
2. **v2's Spearman of 0.7847 is close to the ceiling, not evidence of a package
   defect.** It sits 0.054 below the mean within-language value. Part of that
   gap is the different generator (v2 used `random_permutation`, which was
   incorrect), but the measurement above shows the metric has a hard ceiling
   regardless of generator, so 0.90 was never attainable.
3. **The Jaccard gate has the same structural problem in milder form.**
   Between two independent R runs the Jaccard of the selected sets ranges from
   0.43 to 0.83, with only 4 to 6 features selected per run. At that set size
   the statistic is extremely quantised, and the frozen `>= 0.80` threshold
   is only met by the most favourable pairs. A support-set agreement metric
   needs either a set size large enough to be stable or a different estimand.
4. **The FDP-threshold gate is currently failing for a different reason.** The
   five R runs give thresholds of 0.70 to 0.77 against the frozen Python value
   of 0.58, a delta of 0.12 to 0.19 against a threshold of 0.05. This is a real
   discrepancy in the estimator, not Monte-Carlo noise: it exceeds the seed-to-
   seed spread of 0.07. It is the gate most worth investigating, because unlike
   Spearman it is measuring a systematic difference rather than a noise floor.

**What this changes about the release.** No OOL parity number should be quoted
from the current protocol, and the protocol's Spearman and Jaccard thresholds
need revision before any full-profile run is worth its compute. The revision
should either raise the replicate count and average the Spearman over pairs of
independent runs, or replace the point gate with a comparison against the
measured within-language ceiling.

The full-profile run recommended as item 2 of this report is therefore
**deferred**: it cannot pass the current gates, and running it would produce
another sealed negative packet that says nothing new.

## Actions taken

1. The 0.808 figure is removed from the manuscript and every paper artifact that
   restates it, and the Jaccard sentence is re-anchored to the sealed v2 packet
   with its `not_ready` status stated.
2. The v3 smoke figures are labelled as a degenerate 2-bootstrap smoke wherever
   they appear, not as a parity result.
3. `README.md` already carries the correct v2 triple and is left unchanged.

## Required before any OOL number is quoted again

1. **Bound the achievable Spearman.** Run the R side at 500 bootstraps on the
   pinned matrix, then resample the same 500 bootstrap index sets at several
   seeds and report the Spearman between two R runs. That is the
   within-language Monte-Carlo ceiling. If it sits near 0.8, then v2's 0.785 and
   the 0.1.0-era 0.808 are at the noise floor and the `>= 0.90` gate is
   unreachable by construction — in which case the gate, not the package, must
   change under a new protocol version. This is the single most likely
   explanation for a persistent sub-0.9 Spearman and it is currently untested.
2. **One full-profile run** at 500 bootstraps, 10 pinned lambdas, seed 42,
   `knockoff_equi` with an empty fallback history, against a candidate built from
   final `main`. This is the first and only measurement in which the three
   statistics are interpretable.
3. **Strengthen or delete the uninformative gates** (`lambda_alignment`,
   `generator_alignment`, `preprocessing_alignment`) and add a test asserting
   each gate can fail.
4. **Add the coverage the OOL contract lacks**: nothing currently computes a real
   Jaccard, Spearman or threshold delta; nothing fits the real 1317-column path;
   nothing pins the `python_max_score` semantics against the pinned
   `stabl.py` body; nothing verifies the pinned `median`/`mean`/`scale` against
   the raw inputs.
5. **Repair the two broken provenance chains**: the smoke's missing `governing/`
   directory and orphaned hashes, and the divergence between
   `load_ool_data()`'s 100-feature bundle and the 1317-feature parity dataset in
   the methods text.

## Explicit non-claims

This report establishes where each OOL number came from. It does not establish
that `stablr` matches the Python reference: no promotable OOL measurement exists.
It does not predict what the full profile will produce. It does not treat the
`>= 0.90` Spearman gate as correct merely because it is frozen; item 1 above may
show it is unreachable.

Interim recommendation: while no promotable OOL measurement exists, the
manuscript should not claim OOL parity at all. The supported claim is narrower —
deterministic algorithm, ranking, and support parity against the pinned Python
STABL reference on synthetic fixtures, which is what
`tests/testthat/fixtures/python_parity/` actually establishes.
