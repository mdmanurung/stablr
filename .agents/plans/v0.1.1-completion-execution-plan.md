# stablr v0.1.1 Completion Execution Plan

## Objective and current terminal point

Implement and verify every release-completion component that does not require an
independent scientific decision. Produce review-ready, tamper-evident SCI-04 and
OOL v3 materials, hardened candidate-bound CI, OOL evidence closure, and an
evidence-only outer promotion validator. Stop with release contract v1 still
non-promotable until two separately accepted, authenticated reviewer decisions
exist. CRAN submission and publication are deferred.

## 1. Preserve the baseline

1. Reconfirm the package branch, SHA, dirty files, remote state, and the sibling
   `stablr-experiments` state before editing.
2. Preserve all historical RE-01, methodology, OOL v2, failed, and incomplete
   evidence. Never write into historical artifact directories.
3. Keep `papers/cell-reports-methods/` entirely out of scope.
4. Use only fresh no-replace paths below the completion campaign root. Describe
   chmod-plus-manifest evidence as sealed and tamper-evident, not truly
   immutable unless copied to separately controlled retention/WORM storage.

## 2. Make the independent reviews executable

1. Preserve SCI review packet v1. Add a new versioned SCI/methodology packet
   that states the actual matrix: 96 declared cells, eight fixed-X/high-
   dimensional cells proposed as `not_applicable`, 88 applicable cells, and 44
   applicable null cells. Ask the reviewer to decide the estimand, confidence
   bound, multiplicity family, threshold, replicate count, malformed-data
   handling, exact reference values, and applicability policy.
2. Preserve OOL protocol v3 and construct a hash-manifested review bundle that
   binds the protocol, generator, v3 reference binding, relevant schemas,
   negative v2 evidence identity, and review checklist.
3. Define separate SCI and OOL decision schemas. Both must bind the complete
   proposal/review-bundle manifest, carry an accepted/rejected decision, and
   reference an actual decision record.
4. Define an authenticated reviewer trust interface for automatic promotion:
   an externally supplied allowlisted identity and public-key fingerprint plus
   a detached signature over the decision record (or an equivalently
   authenticated intake receipt). Verification must fail closed when the trust
   root, decision file, signature, hash, scope, or accepted status is missing or
   mismatched. Do not populate or self-approve a reviewer trust root.
5. Keep reviewer identity and signatures outside the package tarball. Future
   contract v2 will contain only consent-safe decision IDs and cryptographic
   hashes that bind the external sealed decision bundle.

## 3. Harden OOL v3 before scientific use

1. Extend the CLI with actual decision-record and trust/signature inputs. Read
   and hash the record, validate its target and status, authenticate it, and
   include copies of the governing protocol, approval, decision, signature,
   review manifest, generator, and reference binding in the packet closure.
2. Add exact score-profile alignment: 1,317 unique, finite, identically named
   R and Python scores are required before Spearman is computed. Partial
   intersections cannot pass.
3. Execute from a clean, exact experiments commit or sealed Git bundle; record
   commit/tree/bundle identity and reject unrelated or manuscript content from
   review and promotion bundles.
4. Use the prepared release context where possible, or reproduce its isolated
   candidate installation, dependency closure, runtime identity, native-library
   hashes, and sanitized environment. Outer promotion must require package and
   OOL runtime/candidate equality.
5. Add an independent packet verifier. It must reject symlinks/non-regular
   files, extra or missing files, schema drift, candidate disagreement,
   non-full profiles, inconsistent gate summaries/seals, and any transitive
   hash mismatch.
6. Preserve seal-last/no-replace behavior. Smoke always seals FAIL and can
   never promote.

## 4. Add exact-candidate CI and promotion validation

1. Extend the manual candidate workflow so one build job creates
   `stablr_0.1.1.tar.gz`; every downstream job downloads that artifact and
   verifies its SHA-256 before installation/checking. Downstream jobs must not
   rebuild the package.
2. Cover Linux release/devel/oldrel, macOS release, Windows release, minimum R
   4.1, clean-install smoke, and coverage where feasible. Emit and upload a
   receipt per job binding tarball SHA, Git SHA, run/attempt, OS, R version,
   result, and relevant log hash.
3. Keep ordinary PR CI separate from exact-candidate CI. Describe R-hub checks
   truthfully as exact-Git-SHA specialist checks unless they consume and verify
   the candidate tarball.
4. Add an external promotion-record schema, CLI/validator, and tests in
   `stablr-experiments`. The evidence-only policy must require authenticated
   SCI/OOL decisions, one candidate SHA everywhere, passing package and OOL
   packets, required exact-candidate receipts, specialist receipts, runtime
   equality, and final external CRAN-comments hash. Write the seal last.
5. Do not create a passing promotion record from fixtures, smoke runs, draft
   records, missing services, or unsigned decisions.

## 5. Preserve v1 and defer scientific contract v2

1. Keep release-contract v1, its schema, validator, fixtures, and historical
   packets unchanged and non-promotable.
2. Do not implement the SCI formula, replicate count, multiplicity, applicability
   semantics, methodology artifact-schema bumps, or promotable contract v2
   until the SCI decision exists.
3. Record the additive migration requirements for the post-review continuation:
   schema-dispatched v1/v2 validators; a complete applicability matrix as
   contract data; explicit `not_applicable` reason codes; no fallback in an
   applicable cell; methodology gate/artifact schema version bumps; one
   canonical source of settings; and reviewer-supplied deterministic tests.
4. Contract v2 must count multiplicity over reviewer-approved applicable cells,
   not a hardcoded 48, and must use the reviewer-approved replicate count.

## 6. Documentation, verification, and local provenance

1. Reconcile NEWS, package docs, release docs, experiments README, and CLI docs
   with the evidence-only outer policy. Remove stale claims that historical OOL
   v2 used a final candidate and resolve conflicting R4_51 paths.
2. State that package Release Evidence is necessary but insufficient; OOL v3
   and the outer record are mandatory. Keep `cran-comments.md` draft and put the
   future exact-results text outside the frozen repository.
3. Add tests for every new failure mode, including malformed/forged decisions,
   transitive closure tampering, partial score profiles, workflow matrix and
   checksum behavior, receipt mismatch, and promotion-record tampering.
4. Run focused tests, full package tests with optional dependencies, OOL tests,
   documentation generation, source build, isolated install, `R CMD check
   --as-cran`, pkgdown, and `git diff --check`. Record all skips and host-only
   warnings precisely; do not call them release passes.
5. Create atomic local commits in the package repository and a clean local
   release commit in `stablr-experiments`, excluding manuscript content. Export
   a content-addressed, hash-manifested local Git bundle for experiments.
6. A branch push and draft PR are allowed only through already configured
   noninteractive credentials. Do not modify credentials or force-push.

## 7. Stop and continuation conditions

Stop after the pre-review implementation when either independent decision is
absent. Report exactly what is technically complete and provide the two bundle
paths/hashes needed by the reviewer.

After authentic accepted decisions are supplied in a later continuation:

1. Implement additive contract v2 and reviewer reference tests.
2. Merge through green PR CI, freeze one candidate, and run cheap artifact-
   bound platform checks before expensive science.
3. Prepare one R4_51 context, then run methodology, late fusion, and full OOL
   against the identical tarball in fresh attempt roots.
4. A completed failed gate is retained and stops release; a crash is unsealed
   and may be retried only with identical settings in a new root.
5. Seal the outer evidence-only promotion record only after all evidence and
   platform receipts pass.
6. Stop at the sealed submission-ready bundle. Do not submit to CRAN, tag,
   publish a GitHub release, change branch protection, or bump the development
   version without new explicit authorization.
